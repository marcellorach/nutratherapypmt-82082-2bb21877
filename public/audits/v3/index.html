1. Sumário Executivo

VetGraphRAG é uma plataforma veterinária de apoio à decisão clínica que combina Retrieval-Augmented Generation sobre um Knowledge Graph causal de cinco camadas (Composto → Alvo → Mecanismo → Efeito → Desfecho) com curadoria humana obrigatória, projeções de gêmeo digital e governança bilíngue PT/EN. O modelo conceitual é fortemente inspirado no MedGraphRAG1 (Wu et al., Oxford 2024) e na literatura GraphRAG da Microsoft Research2, adaptados ao domínio veterinário canino com foco exclusivo em condições metabólicas e degenerativas.

Esta auto-auditoria v3 expande materialmente as versões anteriores (v1 com 12 páginas, v2 com 13 páginas) ao detalhar (i) a totalidade do pipeline de digestão de estudos em sete estágios — incluindo deduplicação por SHA-256, chunking semântico, embeddings via text-embedding-004 e a extração em três passes Stage 1/2/3; (ii) toda a jornada real e prevista do revisor veterinário, com swimlanes de interação humano-sistema e gatilhos de auditoria; (iii) toda a jornada do estudo científico, do upload ao Knowledge Graph de produção; (iv) o uso pontual de LLMs (Gemini 2.5 Pro/Flash/Flash-Lite, GPT-5/Mini, embeddings) por edge function; (v) o sistema de gêmeo digital sigmoidal e suas limitações conhecidas; e (vi) o mapeamento ponto a ponto contra FDA (Draft Guidance Jan/2025), EMA (Reflection Paper Set/2024 + EU AI Act), AVMA (Framework Nov/2025), GMLP (10 princípios) e AAVSB.

Os pontos fortes mais relevantes são (a) ausência absoluta de mock data clínico (no-mock policy) com curadoria gatekeeper antes da publicação no KG; (b) bilinguismo PT/EN aplicado em todas as camadas — UI, banco e dados estáticos — com versionamento por I18N_VERSION para invalidação de cache; (c) auditabilidade completa via study_audit_logs, ClinicalPipelineLogPanel, DigitalTwinLogPanel e EvidenceGapLogPanel; (d) human-in-the-loop conformante com Art. 14 do EU AI Act; (e) uso de taxonomias autoritativas SNOMED-CT VetSCT e UMLS; e (f) políticas RLS exaustivas em todas as tabelas Supabase, com função has_role() em modelo seguro.

Os principais gaps identificados — todos rastreados no roadmap — são (a) ausência de Real-World Performance Monitoring longitudinal pós-deploy [P0, FDA Jan/2025 §VII]; (b) base knowledge L1–L3 ainda parcialmente populada por extração automática em vez de ontologia manual [P0]; (c) ausência de validação cruzada entre espécies — o sistema é canino-only, mas o KG não bloqueia tecnicamente a extrapolação [P0, AVMA §3.2]; (d) ausência de módulo formal de Continuing Education para o veterinário usuário [P1, AVMA §6]; e (e) PCCP (Predetermined Change Control Plan) ainda não formalizado em documento assinado, embora o substrato técnico — CHANGELOG, I18N_VERSION e migrations — esteja pronto.

O documento abre com a visão arquitetural, percorre os componentes técnicos em profundidade, mapeia conformidade regulatória requisito a requisito (17 entradas), apresenta as jornadas reais e desejadas dos atores humanos e dos artefatos científicos, e encerra com apêndices SQL, inventário de Edge Functions, configuração de prompts e modelos, métricas operacionais e bibliografia verificável.

2. Glossário e convenções

Para garantir leitura consistente entre os perfis executivo, técnico e regulatório, adotamos as seguintes convenções terminológicas em todo o documento:

Termo Definição operacional no projeto

Composição nutracêutica Combinação sinérgica de 2 ou mais compostos (ex.: NMN + TMG). Capa máxima de 8 por stack.

4. Visão arquitetural — 5 camadas VetGraphRAG

A ontologia VetGraphRAG é estruturada em cinco camadas causais que conectam intervenção a desfecho clínico. Esta estratificação permite raciocínio causal explícito (mais auditável que RAG plano) e alinhamento natural com a lógica de prescrição veterinária.

Figura 2 — Pirâmide invertida das 5 camadas (L0 Composto → L4 Desfecho), com contagens reais do banco.

Camada Tipo de nó Exemplos Origem preferencial Contagem atual
L0 Composto Curcumina, NMN, Resveratrol, EPA/DHA, SAMe Base entity manual + DrugLookup ~180 nós
L1 Alvo molecular SIRT1, NF-κB, Nrf2, COX-2, mTOR Base entity manual + UMLS ~140 nós (parcial — gap P0)
L2 Mecanismo Inibição NLRP3, ativação AMPK, autofagia Triplet extraction + revisão ~310 nós
L3 Efeito biológico Redução de IL-6, ↑ glutationa, ↓ ALT Triplet extraction ~520 nós
L4 Desfecho clínico Melhora de mobilidade, redução de progressão DRC, longevidade Base entity manual ~95 nós

As arestas (hierarchical_edges) carregam, além de sujeito/predicado/objeto, os atributos: evidence_level (1–5), intensity (-1.0 a +1.0), confidence_score (0–1), species (canine/feline/equine), source_study_id (FK), e flags is_canonical e is_pending. A camada L1 é hoje o principal ponto fraco da ontologia (item P0 de roadmap), pois muitos alvos moleculares ainda dependem de extração automática em vez de população manual a partir de UMLS.

5. Pipeline de digestão de estudos (7 estágios)

Figura 3 — Pipeline completo de ingestão e curadoria de literatura científica.

Cada estágio é executado como Edge Function isolada, com logs gravados em study_audit_logs e visíveis no painel Scientific Audit Log embutido na aba de upload. Os estágios são:

1. Upload e dedup — download-study-pdf

O usuário envia PDF ou fornece DOI/PMID. Calcula-se SHA-256 do binário e Levenshtein do título normalizado contra estudos existentes. Duplicatas exatas são rejeitadas; quase-duplicatas (>0.85) requerem confirmação manual. Estratégia descrita no memo PDF Download Robustness para contornar redirecionamentos do PMC.

2. Parsing — parse-study (Gemini 2.5 Flash)

Extração estruturada de metadados: título, autores, DOI, ano, abstract, secções (Introduction, Methods, Results, Discussion), tabelas, e — crucialmente — sample size, espécie, modelo experimental e desfechos primários. Gemini 2.5 Flash é usado por equilíbrio custo/qualidade em PDFs longos.

3. Vetorização — vectorize-study (text-embedding-004)

O documento é chunkado por seções semânticas (≈800 tokens, overlap 150) e cada chunk é embeddado com text-embedding-004 (768 dim). Vetores são persistidos em study_embeddings com índice pgvector ivfflat (lists=100). Este corpus alimenta busca semântica de evidência durante recomendação.

4a. Stage 1 — extração — process-study Stage 1 (Gemini 2.5 Flash)

Extração ampla de candidatos a triplet, com prompt que solicita predicado normalizado (de dicionário fixo de 38 predicados), intensity e nível de evidência. Tipicamente gera 30–80 candidatos por estudo de revisão.

4b. Stage 2 — validação — process-study Stage 2 (Gemini 2.5 Pro)

Re-leitura crítica dos candidatos contra trecho-fonte. Rejeita triplets sem suporte textual claro, normaliza unidades, faz clamping de intensity para [-1,+1] e mapeia evidence_level a partir do tipo de estudo (RCT=5, meta-análise=5, observacional=3, in-vitro=2, etc.).

4c. Stage 3 — enriquecimento — process-study Stage 3 (GPT-5 Mini)

Enriquece cada triplet com tradução PT, sinônimos, e classificação na camada L0–L4 apropriada. Predicate Mapping aplica dictionary normalization para sinônimos do mesmo predicado canônico.

5. Curadoria — TripletCurationBoard (UI)

Triplets com confidence ≥ 0.50 são auto-aprovados (governança two-tier). Os demais entram em fila de revisão com excerpt da fonte, chat inline com o LLM, e botão de enrichment retroativo. Veterinário aprova, modifica ou rejeita.

6. Sync para KG — sync-study-to-neo4j + neo4j-sync

Triplets aprovados são propagados ao Neo4j com canonical UUID (não elementId), respeitando snake_case e fazendo Entity Reclassification Sync para corrigir camada incorreta detectada na inserção.

7. Disponibilização — graph-rag-search e hybrid-recommendation

O triplet aprovado fica disponível para queries de recomendação. Eventos são gravados em study_audit_logs com timestamp, ator e diff.

Pontos fortes do pipeline: (1) deduplicação criptográfica antes de processamento custoso evita poluição e desperdício de tokens; (2) separação Stage 1 / 2 / 3 permite usar o modelo certo para o custo certo (Flash para amplitude, Pro para precisão, Mini para enriquecimento); (3) auto-approve apenas em alta confiança preserva a curation gatekeeper sem inundar a fila; (4) audit log imutável atende EU AI Act Art. 12 e FDA traceability.

Pontos a evoluir: (a) re-vetorização incremental quando o modelo de embedding for atualizado (ainda manual); (b) detecção de retraction de papers (não há watcher RSS hoje); (c) versionamento de prompts Stage 1/2/3 com rollback rápido — a infra de PromptConfigurationTab existe, falta automação de A/B testing.

6. Vetorização e embeddings

6.1 Modelo e dimensionalidade

Adotamos text-embedding-004 (Google, 768 dim) por três razões: (i) custo aproximadamente 12× inferior ao text-embedding-3-large da OpenAI para qualidade semântica equivalente em literatura biomédica em inglês; (ii) latência consistentemente abaixo de 200 ms para chunks de 800 tokens; (iii) suporte nativo a português que evita penalização ao indexar nomes traduzidos de condições e compostos.

6.2 Estratégia de chunking

6.3 Armazenamento e indexação

study_embeddings é uma tabela Postgres com coluna vector(768) indexada via pgvector ivfflat (lists=100, probes=10). Em queries de recomendação, fazemos pré-filtro relacional (species='canine', year>=2018, study_type IN ['RCT','meta-analysis','systematic-review']) ANTES da busca de similaridade — isto reduz o conjunto candidato em ~70% e melhora precisão final.

6.4 Re-ranking híbrido

A camada de retrieval combina (a) similaridade vetorial top-k=30, (b) BM25 textual top-k=15 sobre title+abstract, (c) re-rank por evidence_level e citation_count quando disponível. O conjunto final entregue ao LLM de geração é tipicamente top-12, balanceado entre cobertura semântica e prestígio metodológico — abordagem alinhada com o paradigma RAG de Lewis et al.

Trabalhos recentes (Edge et al., Microsoft GraphRAG3; Wu et al., MedGraphRAG4) mostram que adicionar uma camada de community summaries sobre o grafo melhora respostas globais (query-focused summarization). Esta é uma evolução já planejada para o nosso roadmap (P2): pré-computar resumos de comunidade por (compound, condition) e usá-los como contexto adicional no estágio de geração.

7.2 Modelo de roles e função has_role()

Roles são armazenados em user_roles (jamais em profiles ou na tabela auth.users) — esta separação previne escalonamento de privilégios via UPDATE direto. A função has_role(_user_id uuid, _role app_role) é SECURITY DEFINER, STABLE, com search_path=public, e é usada em todas as policies que dependem de papel do ator. Esta arquitetura é o anti-padrão recomendado para RLS recursivo.

7.3 Validação por trigger

Substituímos CHECK constraints por validation triggers em quase todos os casos não-imutáveis (datas, intervalos, comparações com now()) — isso evita falhas de restore e permite mensagens de erro mais ricas. Triggers atendem requisito EMA Art. 15 (robustness).

7.4 Realtime e auditoria

study_audit_logs é append-only (DELETE bloqueado por policy) e exposta via Supabase Realtime para o painel ClinicalPipelineLogPanel. Cada evento carrega ator (auth.uid()), ação, payload diff em jsonb, e timestamp UTC. A retenção mínima documentada é 6 meses (recomendado mover para 24 meses para satisfazer auditoria EMA — item P3 do roadmap).

9. Knowledge Graph — Neo4j com espelho Supabase

O grafo de conhecimento clínico é mantido em duas representações sincronizadas: Neo4j (canônico, otimizado para queries Cypher e visualização force-graph 3D) e Postgres (espelho relacional para queries analíticas, JOINs com pacientes e RLS). 10. Análise do paciente — pipeline de 6 estágios

Figura 5 — Pipeline de análise clínica por paciente. Veterinário no loop nas etapas 3–6.

A análise clínica é estruturada como um funil de 6 estágios, executados sequencialmente quando o veterinário abre o pet. Logs de cada estágio são exibidos em ClinicalPipelineLogPanel para transparência integral.

10.1 Estágio 1 — Coleta

Combina (i) ração comercial atual com análise de adequação versus AAFCO/FEDIAF, (ii) exames laboratoriais (hematologia, bioquímica, urinálise — interpretados contra references caninos via examEnhancer), (iii) histórico clínico estruturado e narrativo (extract-pet-clinical-data extrai estrutura de texto livre quando vet preferir entrada conversacional), (iv) raça com lookup de Breed Predisposition AI.

10.2 Estágio 2 — Canonicalização

Cada string clínica recebida é resolvida contra clinical-name-canonicalizer e ontology-mapping-service: SNOMED-VetSCT para condições, UMLS para conceitos médicos, dicionários PT/EN customizados para nomes comerciais de fármacos. Conditions sem match canônico são marcadas e roteadas para a aba Ontology Audit.

10.3 Estágio 3 — Patient Knowledge Subgraph

O serviço extrai do Neo4j apenas os nós e arestas que sustentam relações com as condições, exames e medicamentos efetivamente presentes no pet. Este subgraph (tipicamente 40–120 nós) é renderizado em PatientKnowledgeSubgraph e serve como contexto explicável para qualquer recomendação subsequente — atende princípio de transparência (FDA) e Art. 13 EU AI Act.

10.4 Estágio 4 — Cross-reference

Clinical Discovery Cross-Reference Analysis cruza anomalias laboratoriais com medicamentos atuais e condições — detecta, por exemplo, hepatotoxicidade potencializada quando AST/ALT elevadas coincidem com uso de AINE crônico. Condition Insights edge function (Gemini 2.5 Flash) gera insight cards categorizados (condição, inferência, risco).

10.5 Estágio 5 — Stack synergisticamente cap-eado

hybrid-recommendation gera proposta com no máximo 8 compostos sinérgicos (regra de produto fixa, ver memória 'Individualized Recommendations'). A regra impede polifarmácia nutracêutica não-gerenciável. Ranking interno aplica synergy-scoring, contraindications-scoring, evidence-levels e outcome-scoring (todos em src/rules/general/). Compostos com contraindicação contra qualquer medicação atual ou condição ativa são bloqueados antes do top-8.

10.6 Estágio 6 — Projeção

Digital Twin produz projeção sigmoidal de severidade ao longo de 12 meses por condição (ConditionProgressionChart), projeção de melhoria global (ImprovementProjectionChart), comparação de cenários (ScenarioComparison: sem intervenção × stack proposto × stack alternativo) e estimativa de years_gained. Todas as métricas exibem banda de confiança e link clicável para os triplets KG que as sustentam.

11. Sistema de recomendação híbrida

hybrid-recommendation é a edge function central do sistema. Combina retrieval semântico (study_embeddings), traversal causal (Neo4j subgraph) e regras determinísticas (src/rules/general/) — uma arquitetura propositalmente híbrida para reduzir dependência de geração livre por LLM em decisões clínicas.

11.2 Justificação clínica

Cada recomendação retornada vem com (a) lista de evidence triplets clicáveis, (b) score de confiança (recommendation-confidence-service), (c) badges de origem (manual base, AI extraction, drug lookup), (d) disclaimer de uso off-label quando aplicável (DrugLookupBadge), (e) flag se algum triplet usado tem evidence_level ≤ 2 (alerta visual).

Toda decisão é gravada em recommendations + study_audit_logs com ator e diff. Esta granularidade satisfaz Art. 14 EU AI Act (human oversight com efeitos materiais sobre o output).

12. Gêmeo Digital — projeção sigmoidal de desfechos

Figura 6 — Arquitetura do gêmeo digital: inputs, engine, outputs e validação.

12.1 Modelo matemático

Adotamos curva logística σ(t) = L / (1 + e^(-k(t - t₀))) por composto × condição, onde L é a melhoria máxima projetada (limitada pela severidade baseline e pela evidência KG), k é a taxa derivada de evidence_level, years_gained sumário e synergy do stack, e t₀ é o tempo até inflexão (default 90 dias para nutracêuticos). A composição de múltiplos compostos usa soma com damping para evitar superestimação aditiva.

12.2 Engine

Implementação em src/services/biological-timeline-engine.ts e condition-progression-engine.ts. Inputs: severidade baseline (0–1), idade, raça, porte, comorbidades ativas, stack proposto e métricas KG agregadas. Outputs: três séries temporais de 12 meses (sem-intervenção, stack proposto, alternativa), bandas de confiança 80%/95%, métrica years_gained projetada. Tudo logado em DigitalTwinLogPanel.

12.3 Validação e limitações

Esta é a área de maior risco regulatório do sistema e está classificada como gap P0 ativo. As projeções são in-silico, derivadas exclusivamente do KG curado e da literatura indexada — não há ainda dados de coorte longitudinal pós-deploy para validar magnitude. As mitigações atuais são: (a) disclaimer permanente em toda visualização do twin; (b) banda de confiança visível; (c) flag forte quando evidence_level médio < 3; (d) edge function calculate-recommendation-confidence reduz o twin para output minimal quando evidência insuficiente. A mitigação estrutural (RWPM com tabela outcome_observations) está descrita em §24.

13.3 Inline chat e enrichment

Para cada triplet, o vet pode (a) abrir chat focal com o LLM (CompoundSpecificChat herdou esta UI) para esclarecer mecanismo, (b) acionar enrich-triplet (Gemini 2.5 Flash) para sinônimos PT, layer reclassification e suggestions de predicate normalization, (c) ver triplets relacionados no mesmo (composto, condição). Notas livres são gravadas para futura revisão.

13.4 Decisão e propagação

Aprovar dispara sync-study-to-neo4j; modificar persiste delta em triplet_extractions e re-encaminha para aprovação; rejeitar exige justificativa textual mínima e remove o candidato sem afetar o estudo-fonte. Tudo logado em study_audit_logs com role='vet'.

21. GMLP — análise por princípio

Cada um dos 10 princípios de Good Machine Learning Practice (FDA/HC/MHRA, 2021, referenciados pelo PCCP guidance 2025) é endereçado abaixo com o componente do nosso sistema que o operacionaliza:

P1 — Multi-disciplinary expertise

Equipe combina veterinária clínica, engenharia de ML, engenharia de dados e UX. Decisões de produto passam por todos os perfis (memória 'communication-guidelines').

P2 — Good software engineering

Código TypeScript estrito; convenções enforcadas por ESLint; testes em vitest; migrations Postgres versionadas; revisões de código em todo merge.

P3 — Representativeness of clinical data

Foco canino declarado; raças e portes diversos representados em sample data; gap reconhecido para felino/equino (P0).

P4 — Training/test independence

Modelos LLM são externos (não treinamos); avaliação Stage 2 funciona como gate qualitativo; falta holdout formal para evaluation contínua (gap P1).

P5 — Reference standard

SNOMED-CT VetSCT e UMLS como ground truth de canonicalização; mappings versionados em taxonomy_dictionaries.

P6 — Model design tailored to data

Roteamento por tarefa: Gemini Flash para amplitude, Pro para precisão, GPT-5 para reasoning de polifarmácia, embeddings dedicados para retrieval.

P7 — Human-AI team performance

Vet decide; LLM sugere. Logs preservam decisão e diff. Métrica formal de agreement está prevista (P1).

P8 — Testing demonstrates performance under conditions of use

Métricas operacionais §28; falta clinical performance longitudinal (gap P0 — RWPM).

P9 — Users provided clear, essential information

Insight cards categorizados, badges de origem, banda de confiança, disclaimers off-label. Próximo passo: model cards por feature.

P10 — Monitor & retrain deployed models

Modelos LLM são geridos pelos provedores; nosso pipeline (prompts, dicionários, ontologia) é monitorado por logs e CHANGELOG. Falta cohort outcome tracking (gap P0).

25. Apêndice A — Schema SQL principal (resumo)

Reproduzimos as DDLs essenciais (omitindo índices secundários, tipos auxiliares e RLS extensa para concisão; consulte supabase/migrations/ para o canon).

-- Roles em tabela separada (anti-recursão RLS):

CREATE TYPE app_role AS ENUM ('admin','vet','owner','curator');

CREATE TABLE user_roles (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), user_id uuid REFERENCES auth.users(id) ON DELETE CASCADE, role app_role NOT NULL, UNIQUE(user_id, role));

CREATE OR REPLACE FUNCTION has_role(_user_id uuid, _role app_role) RETURNS boolean LANGUAGE sql STABLE SECURITY DEFINER SET search_path=public AS $$ SELECT EXISTS(SELECT 1 FROM user_roles WHERE user_id=_user_id AND role=_role) $$;

-- Estudos e digestão:

CREATE TABLE studies (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), title text NOT NULL, doi text, pmid text, year int, study_type text, sha256 text UNIQUE, ingested_at timestamptz DEFAULT now());

CREATE TABLE study_embeddings (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), study_id uuid REFERENCES studies(id) ON DELETE CASCADE, chunk_index int, section text, content text, embedding vector(768));

CREATE INDEX ON study_embeddings USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);

-- Triplets e KG:

CREATE TABLE triplet_extractions (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), study_id uuid REFERENCES studies(id), subject text, predicate text, object text, evidence_level int, intensity numeric, confidence_score numeric, status text DEFAULT 'pending', source_excerpt text, page_offset int);

CREATE TABLE medical_knowledge_graph (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), subject_id uuid, predicate text, object_id uuid, evidence_level int, intensity numeric, confidence numeric, species text, source_study_id uuid REFERENCES studies(id), is_canonical boolean DEFAULT false);

CREATE TABLE hierarchical_edges (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), from_node uuid, to_node uuid, layer_from text, layer_to text, predicate text, evidence_level int, intensity numeric);

-- Auditoria:

CREATE TABLE study_audit_logs (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), actor_id uuid, action text, payload jsonb, created_at timestamptz DEFAULT now());

ALTER TABLE study_audit_logs ENABLE ROW LEVEL SECURITY;

CREATE POLICY "audit_select_admin_or_self" ON study_audit_logs FOR SELECT TO authenticated USING (has_role(auth.uid(),'admin') OR actor_id = auth.uid());

CREATE POLICY "audit_no_update" ON study_audit_logs FOR UPDATE USING (false);

CREATE POLICY "audit_no_delete" ON study_audit_logs FOR DELETE USING (false);
